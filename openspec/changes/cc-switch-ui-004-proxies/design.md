# Design

## Context

ProxyPage 与 KProxyPage 是各自 Panel 的外层页头；ProxyPanel 混合状态订阅、配置表单、统计及多个弹窗。ProxySecurityPanel 还有 TLS、自签证书、审计与 needsRestart 轮询。ProxyPoolPage 同时拥有导入、策略、过滤、链路诊断与账号分配面板。多种系统操作与运行态使本变更需要显式设计。

依赖 001 公共 Token／控件和 002 PageHeader；P01～P08 为功能基线。003 的账号绑定入口只消费同一 store，无需改其调用协议。

## Goals / Non-Goals

**Goals:** 三页采用一致的服务状态与配置分区，保证运行中／失败／需重启状态和所有原参数清晰可见。

**Non-Goals:** 不统一 API 反代和 MITM 的业务模型，不新增路由模式或证书机制，不改网络层及服务协议。

## Decisions

1. **页面按现有业务分开。** 三个独立 PageType 保留；各用公共页头。反代／KProxy 的服务启停为主要操作，运行信息为紧邻状态；代理池保留添加／导入、策略、验活和绑定分区。直接合并为一个服务中心会改变导航和状态归属，本轮不采用。
2. **反代按基础接入、账号与调度、模型／客户端、请求高级、安全、统计／日志分区。** 使用统一 Card／表单与现有折叠结构整理，全部现有字段和 needsRestart 提示保留。即时更新不改为统一保存，原本需要重启的设置也不新增自动重启。
3. **弹窗逐个接入呈现规范。** Models、ModelMapping、ClientConfig、AccountSelect、ApiKeyUsage、ProxyLogs、ProxyDetailedLogs 的标题／内容／操作区统一；保留数据源、选择、复制、验证、关闭与清理。ApiKeyManager 与 SecurityPanel 的内嵌表单继续在原状态所有权下运行。
4. **代理池工具区与绑定区独立。** 搜索和高级筛选放列表前，选中时出现批量工具；账号分配面板沿用独立统计和展开状态。为避免误改目标，不引入新的“可见即全选”逻辑。条目长 URL 可截断并沿原复制功能取得完整值。
5. **KProxy 明确证书和设备动作。** 中性配置面板和状态徽标替换紫色 hero；设备生成、证书导出／安装／卸载保留原处理器及系统权限结果。仅 UI 模拟状态用于展示核对，不在本轮执行系统改动。

## Risks / Trade-offs

- [将即时更新误改为保存按钮提交] → 对照每个原 onChange／onBlur 的 API 调用与运行态，保持生效时机。
- [安全折叠区隐藏重启提示] → needsRestart 按原条件显现，整理视觉不吞掉提示或轮询清理。
- [列表多选与绑定分配范围混淆] → 维持两种集合及原动作名称，以选中子集和全部解绑确认核对。
- [共享日志样式造成清理范围合并] → 请求日志／详细日志／系统日志仍独立，006 不重复修改本成员弹窗。

## Migration Plan

依次迁移三页页头、反代分区与弹窗、KProxy、代理池；每步核对相应 P 项并保留证据。无配置迁移；出现回归回退对应呈现提交。需要真实服务的接口 case 只在隔离实例运行，记录测试环境与受影响 case。

## Implementation refinement

用户于2026-11-26授权实施。沿用001公共UI契约，三页使用002 PageHeader；默认弹窗512px，模型／客户端672px，映射／密钥管理768px，用量／请求日志896px，详细日志1120px，全部限于视口减32。代理池列与操作完整保留，内容最小1120px并独立横向滚动；实际行高和虚拟估值同步58px，50条以上容器明确60vh高度，以保证最小窗口的操作可达。业务字段、生效时机、订阅和IPC保持，测试与外部环境限制见implementation.md。
